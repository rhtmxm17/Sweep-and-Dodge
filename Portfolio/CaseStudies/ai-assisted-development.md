# AI coding agent와 함께 기능을 설계하고 검증한 방식

`Sweep and Dodge`를 개발하면서 AI coding agent를 코드베이스 탐색, 대안 비교, 구현, 반복 검증과 문서화에 일상적인 개발 도구로 사용했습니다.

개발자는 해결할 문제와 변경 범위, 선택 기준을 정하고 최종 결과를 직접 플레이하거나 사용하며 판단했습니다. Agent는 저장소의 코드와 문서를 탐색하고, 대안을 구체화하며, 승인된 방향을 구현하고 반복 가능한 검증을 수행했습니다.

이 글에서는 플레이 감각을 개선한 BroomSweep과 콘텐츠 제작 방식을 교체한 Stage Map Editor를 통해 실제 역할 분담과 작업 흐름을 설명합니다.

## 작업 흐름

AI 활용을 별도의 자동 코드 생성 단계로 분리하지 않았습니다. 일반적인 개발 과정 안에서 탐색과 구현의 왕복을 가속하는 방식으로 사용했습니다.

```text
문제 발견 또는 목표 정의
→ 기존 코드와 문서 탐색
→ 대안과 제약 비교
→ 개발자가 방향 선택
→ Agent가 계획·구현·자동 검증
→ 개발자가 플레이와 사용성 확인
→ 발견한 지식을 다음 작업의 규칙으로 반영
```

| 개발자가 담당한 판단 | Agent가 주로 담당한 실행 |
|---|---|
| 프로젝트 목표와 우선순위 결정 | 관련 코드·문서·테스트 탐색 |
| 요구사항과 변경 금지 경계 정의 | 구현 대안과 파급 범위 제안 |
| 여러 설계안 중 최종 방향 선택 | 승인된 방향을 실행 계획과 코드로 변환 |
| 플레이 감각과 UI·도구 사용성 판단 | Compile, EditMode, PlayMode Smoke 등 반복 검증 |
| 공개할 결과와 주장 강도 결정 | 변경 내용과 검증 결과 정리 |

여러 작업을 거치며 점진적으로 형성된 구조에 대해서는 세부 요소의 최초 제안 주체를 임의로 구분하지 않았습니다. 대신 개발자가 무엇을 문제로 정의했고, 어떤 제약과 선택 기준을 제시했으며, 결과를 어떻게 판단했는지를 구체적인 사례로 설명합니다.

## 사례 1: 플레이 감각을 개선한 BroomSweep

### 어떤 문제가 있었나요?

초기의 청소 동작은 기능적으로 Dust를 제거했지만, 실제 플레이에서는 빗자루질과 연결되지 않는 기계적인 동작으로 느껴졌습니다. 코드는 정상적으로 실행되고 자동 테스트도 통과할 수 있지만, 직접 플레이하지 않으면 발견하기 어려운 문제였습니다.

### 개발자가 정한 목표

- 좌우 방향의 Sweep을 번갈아 실행합니다.
- Sweep 중에는 이동 속도를 제한합니다.
- 동작 중 방향을 크게 돌려 비정상적으로 넓은 범위를 청소하지 못하도록 방향을 고정합니다.
- 구현 후 직접 플레이하면서 시작 각도와 조작 감각을 조정합니다.

개발자는 문제와 주요 행동 제약을 정의하고 Agent에게 추가 대안을 요청했습니다. Agent는 기존 입력과 청소 시스템을 탐색한 뒤 설계 문서와 구현 계획을 작성하고, 선택이 필요한 지점을 확인받아 코드와 자동 검증으로 옮겼습니다.

### 어떻게 마무리했나요?

완성된 Sweep은 좌우 방향을 교대로 사용하고, 활성 구간에는 이동과 방향 전환 제약을 적용합니다. 구현 뒤에는 개발자가 직접 플레이하면서 자동 테스트로 판단할 수 없는 시작 각도의 어색함을 다시 조정했습니다.

이 사례에서는 플레이 문제의 발견과 최종 감각 판단을 개발자가 맡고, 설계 구체화와 구현·반복 검증을 Agent가 맡았습니다. 기능의 완료 기준도 “테스트가 통과하는가”에서 끝나지 않고 “실제로 조작했을 때 의도한 감각이 전달되는가”까지 포함했습니다.

## 사례 2: 제작 흐름을 교체한 Stage Map Editor

### 기존 방식의 문제가 무엇이었나요?

기존 스테이지 제작은 Scene, Tilemap과 여러 Marker를 함께 다뤄야 했습니다. 프로젝트 전용 규칙과 작업 순서를 기억해야 했고, 필요한 데이터를 찾거나 전체 맵 구조를 확인하기 어려웠습니다. HazardActor가 Source 진행도에 따라 언제 등장하는지도 제작 화면에서 미리 파악하기 어려웠습니다.

### 개발자가 정한 범위와 경계

- 전용 Editor Window와 Scene View Tool을 함께 사용합니다.
- 이동 가능 영역, Source, Deposit, Player Start, HazardActor와 Anchor를 편집합니다.
- 기존 Stage 1~3 데이터를 새 제작 방식으로 이전합니다.
- Source 진행도에 따른 HazardActor Encounter를 미리 확인합니다.
- 기존 Runtime Asset과 ECS 계약은 변경하지 않습니다.
- HazardActor Archetype과 발사 Pattern 편집은 기존 전용 도구에 남깁니다.

핵심은 “새 Editor를 만든다”는 목표뿐 아니라 Runtime을 교체하지 않는다는 변경 금지 경계를 함께 제시한 점입니다.

### 어떤 구조를 선택했나요?

Agent는 제작 입력을 하나의 `StageMapDocument`에 모으고, 다음 절차를 거쳐 기존 Runtime Asset에 적용하는 구조를 제안했습니다.

```text
StageMapDocument
→ Validation
→ Dry-run Diff
→ Apply
→ StageLayoutSO / StageDefinitionSO / StageCatalogSO
→ 기존 Runtime ECS
```

Validation Issue가 발생한 위치로 이동하는 기능, 적용 전 변경 내용을 확인하는 Dry-run, 오래된 Apply 계획 거부, Undo 가능한 적용 절차도 함께 제안했습니다. 개발자는 이 구조를 선택하고 Runtime 비변경 경계를 유지하도록 했습니다.

새 Document는 Runtime의 데이터 구조를 대체하지 않습니다. 제작자가 다루는 입력을 통합하고 기존 Runtime Asset을 출력으로 유지하여, Editor 개선이 플레이 시스템의 대규모 변경으로 번지지 않도록 했습니다.

구현 후 개발자가 도구를 직접 사용하면서 Palette를 라디오 버튼으로 변경하고, 목록을 표 형태로 정리하며, Source 진행도에 따른 Encounter Preview를 추가하는 후속 UX를 결정했습니다.

이 사례에서는 개발자가 제작 문제와 범위, 변경 금지 경계와 실제 사용 결과를 판단했고, Agent가 구조적 대안과 구현, 데이터 이전과 검증을 실행했습니다.

## 프로젝트 지식을 반복 가능한 규칙으로 만들었습니다

작업 범위가 넓어질수록 코드와 문서에 흩어진 프로젝트 지식을 다음 작업에서도 일관되게 적용할 필요가 있었습니다. 반복해서 확인한 설계 결정과 오류 패턴을 다음과 같은 규칙으로 축적했습니다.

- Request 단계에서는 직접 Despawn하거나 렌더 상태를 변경하지 않습니다.
- Simulation만 CellMap의 Writer가 됩니다.
- Pool과 FreeList의 Dequeue·Enqueue는 지정된 소유 시스템만 수행합니다.
- ECS 밖의 Native Container에 접근할 때는 Fence dependency를 결합합니다.
- Enableable Request를 처리할 때 Query가 포함하는 Enabled 상태를 명시합니다.
- 예시용 Asset의 값을 별도 근거 없이 고정된 Snapshot Test로 만들지 않습니다.

이 규칙은 AI를 제한하기 위한 별도의 통제 장치가 아니라, 사람과 자동화 도구가 같은 프로젝트 계약을 반복해서 적용할 수 있도록 개발 지식을 구조화한 결과입니다.

## 자동 검증과 사람의 판단을 구분했습니다

Agent는 Compile, Console 확인, EditMode 계약 테스트와 PlayMode Smoke처럼 반복 실행할 수 있는 검증을 수행하는 데 적합했습니다. 이 프로젝트에서는 자동 테스트를 설계 계약 중 관찰 가능한 일부가 후속 변경에서도 유지되는지 확인하는 보조 수단으로 사용했습니다.

반면 다음 항목은 개발자가 직접 판단했습니다.

- 조작감과 행동의 자연스러움
- UI 가독성과 화면 구성
- 렌더링과 연출의 강도
- 콘텐츠 제작 도구의 발견성과 작업 흐름
- 포트폴리오에서 공개할 결과와 주장 강도

테스트 자동화 자체를 독립적인 핵심 전문성으로 제시하지는 않습니다. 반복 가능한 검증과 사람의 감각 판단이 서로 다른 범위를 담당하도록 작업 흐름에 배치한 경험을 설명합니다.

## 배운 점과 현재 방식의 한계

AI coding agent가 참조해야 하는 코드, 설계, 테스트와 문서가 늘어나면 작업에 필요한 맥락도 커집니다. 긴 작업에서는 오래된 전제를 사용하거나 범위를 지나치게 넓게 제안하는 경우가 있었고, 이를 바로잡는 왕복에도 시간이 필요했습니다.

이 경험을 바탕으로 다음 방식을 사용했습니다.

- 작업 목표와 성공 조건을 먼저 작게 정의합니다.
- 설계와 구현 단계를 구분하고 변경 전 승인 범위를 명시합니다.
- 장기 결정과 분기 결과를 작업 보드와 보조 기록으로 공유합니다.
- 코드·문서·검증에서 반복되는 계약을 프로젝트 지침으로 정리합니다.
- 자동 검증으로 판단할 수 없는 결과는 직접 플레이하거나 도구를 사용해 확인합니다.

이 작업 방식의 핵심은 AI가 모든 결정을 대신하도록 만드는 데 있지 않습니다. 개발자가 판단해야 할 문제와 Agent가 가속할 수 있는 실행을 구분하고, 반복 과정에서 얻은 지식을 다음 작업에 재사용하는 데 있습니다.
