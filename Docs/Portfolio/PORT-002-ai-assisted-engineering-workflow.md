## 1. 목적

이 프로젝트는 AI coding agent를 설계 논의부터 코드 생성, 테스트 실행, 문서화까지 이어지는 반복 개발 파트너로 사용했다. 특히 Codex/Claude 계열 agent를 통해 설계 목표 정리, 구현 방안 제안, 코드 생성, 스모크 테스트 실행, 문서 초안을 적극적으로 수행했다.

포트폴리오에서 보여주려는 역량은 단순한 AI 사용 경험이 아니라, 실제 프로젝트에서 AI를 사용하면서 생기는 이점과 비용을 이해하고 작업 흐름에 반영한 경험이다. 핵심은 다음이다.

- 설계 주제와 목표를 사람이 정의하고, agent가 이를 문서화/정교화하도록 사용한다.
- 구현 방안은 agent 제안을 출발점으로 삼되, 요구사항과 기존 구조에 맞는지 검토한다.
- 확정된 플랜에 따라 agent가 코드 생성과 스모크 테스트를 수행하도록 한다.
- 조작 체감, 렌더링, 시각적 품질처럼 사람의 판단이 필요한 영역은 직접 확인한다.
- 컨텍스트가 커질수록 시간/토큰 비용과 수정 왕복 비용이 증가한다는 점을 작업 분해에 반영한다.

## 2. 실제 작업 흐름

### 1. 설계 주제 결정

먼저 이번에 만들고자 하는 것이 무엇인지 결정한다. 대부분은 게임으로서 기능하기 위해 필요한 항목을 채워나가는 방식으로 정했다.

예를 들어 플레이 루프, HUD, 피드백, 스테이지 흐름, 콘텐츠 검증, 대량 탄환 파이프라인처럼 실제 데모를 성립시키는 데 필요한 주제를 순차적으로 다뤘다. 간혹 우선순위가 높은데 누락된 작업이 있는지 AI agent에게 검토를 요청하거나, 다음 작업 후보 자체를 제안받기도 했다.

### 2. 설계 목표 정의

설계 주제가 정해지면, 그 주제가 정확히 무엇을 의미하는지 정리한다. 이 단계는 "무엇을 만들 것인가"를 agent와 공유 가능한 목표로 바꾸는 과정에 가깝다.

이 설계로 이루고자 하는 것, 개념적인 작업 범위, 제외할 범위, 성공 조건을 명확히 하고, AI agent가 정리한 설계 목표가 의도와 다르면 피드백을 통해 조정했다.

### 3. 구현 방안 수립

설계 목표가 정리되면, 이를 어떤 방식으로 구현할지 결정한다. 목표가 명확한 경우 AI agent는 대부분 적절한 구현안을 제안했지만, 항상 충분한 것은 아니었다.

검토 과정에서 특히 문제가 되었던 제안은 다음과 같다.

- 해당 세션에서 agent가 확인하지 않은 코드 영역까지 고려해야 하는 경우
- 이미 존재하는 구조를 놓치고 중복 구현을 시도하는 경우
- 요구사항에 비해 구현 범위가 과도하게 커지는 경우
- DOTS ownership, update order, fence 규칙을 단순화해서 해석하는 경우

이 경우 사람이 피드백을 주거나, 다른 구현 방안을 제시하거나, 작업 범위를 다시 줄이는 방식으로 조정했다.

### 4. 코드 생성 및 테스트

구현 방안이 정리되면, AI agent가 플랜에 따라 코드를 생성하고 테스트를 실행했다. Unity compile, Console error 확인, EditMode, PlayMode smoke 같은 반복 검증은 agent가 수행하기 좋은 영역이었다.

다만 모든 검증을 자동화할 수는 없었다. 조작 체감, 렌더링 결과, UI 가독성, 연출 강도 같은 영역은 사람이 직접 플레이하거나 화면을 확인해야 했다.

## 3. AI가 특히 도움이 된 영역

AI coding agent가 실제로 도움이 된 영역은 다음과 같다.

| Area | Value |
|---|---|
| 작업 후보 검토 | 현재 프로젝트 상태에서 누락된 작업이나 우선순위 후보를 빠르게 제안받을 수 있었다. |
| 설계 목표 정리 | 모호한 요구를 목표, 범위, 성공 조건으로 정리하는 속도가 빨라졌다. |
| 구현안 제안 | 여러 구현 방식을 빠르게 비교하고, 기존 구조에 맞는 방향을 고르는 출발점이 되었다. |
| 코드 생성 | 확정된 플랜을 기준으로 C# 시스템, 테스트, 문서 변경 초안을 생성했다. |
| 테스트 실행 | Unity compile, Console 확인, EditMode, PlayMode smoke 같은 반복 검증을 수행했다. |
| 문서화 | ADR/TD/OPS/Portfolio 문서 초안을 기존 문서 체계에 맞춰 작성했다. |

## 4. 반복 오류 패턴의 지침화

AI agent는 코드 생성 후 빌드나 테스트 과정에서 오류를 발견하고 스스로 수정하는 경우가 많았다. 단발성 오류는 큰 문제가 아니지만, 프로젝트 구조상 같은 유형의 오류가 반복되면 시간과 토큰 비용이 크게 증가했다.

따라서 사람의 역할은 모든 세부 코드를 매번 직접 검사하는 것보다, agent가 반복적으로 생성하고 수정하는 오류 패턴을 관찰해 프로젝트 지침으로 고정하는 쪽에 가까웠다.

반복적으로 지침화한 패턴은 다음과 같다.

- Request 단계가 직접 실행 책임을 가져가지 않았는가
- Simulation 단계 외 시스템이 CellMap writer가 되지 않았는가
- Pool/FreeList Enqueue/Dequeue owner가 분산되지 않았는가
- ECS 밖 Native container 접근에 fence 결합이 빠지지 않았는가
- enableable query가 disabled 상태를 의도치 않게 제외하지 않았는가
- 테스트가 설계 문서의 예시값을 snapshot 기준으로 승격하지 않았는가

이러한 항목은 단순한 코드 리뷰 체크리스트라기보다, agent의 다음 생성 과정에서 같은 실수를 줄이기 위한 guardrail로 사용했다.

## 5. 개발 비용 절감 효과

AI coding agent를 적극적으로 사용하면서 가장 크게 줄어든 비용은 설계 정리, 코드 탐색, 구현 초안 작성, 반복 검증의 왕복이다.

- 새 기능을 추가하기 전 관련 시스템, 테스트, 문서를 빠르게 모을 수 있었다.
- 확정된 설계에 맞춘 C# 구현 초안을 빠르게 생성할 수 있었다.
- 구현 후 문서와 테스트를 같은 맥락에서 갱신하는 비용을 줄일 수 있었다.
- 빌드/테스트 실패 로그를 바탕으로 수정 후보를 빠르게 좁힐 수 있었다.

이 프로젝트의 AI 활용 방식은 "AI가 알아서 설계를 결정한다"가 아니라, 사람이 설계 주제와 목표를 정하고 agent가 구현과 반복 작업을 가속하는 형태다.

## 6. 한계와 리스크

AI coding agent를 실제로 사용하면서 가장 크게 체감한 비용은 컨텍스트 비대화였다. 세션이 길어지고 참조해야 할 설계, 코드, 테스트, 문서가 늘어날수록 응답 시간과 토큰 소비가 커졌다. 그 결과 잘못된 가정이나 중복 구현을 바로잡는 비용도 증가했다.

또한 1차 코드 생성은 종종 빌드 오류나 테스트 실패를 만들었다. 이 경우 agent가 다시 로그를 읽고 수정하는 왕복이 가능했지만, 그 과정 자체도 시간과 토큰 비용을 발생시켰다.

이 경험 때문에 이후 작업에서는 다음 원칙이 중요해졌다.

- 작업 주제와 목표를 먼저 작게 자른다.
- 구현 플랜을 명확히 한 뒤 코드 생성을 요청한다.
- agent가 확인하지 않은 영역을 전제로 한 제안은 다시 검토한다.
- 테스트 실패 수정 왕복이 길어지면 범위를 줄이거나 세션을 분리한다.
- 조작 체감과 시각 결과는 자동 테스트만으로 판단하지 않는다.
