# ADR-20260303-01-replay-min-foundation-and-seed-unification
> OPS-001 #10의 최소 목표로 "동일 머신/동일 빌드 재현" 범위를 고정하고, 입력 프레임 스냅샷 + run seed 계열 RNG 일원화를 도입한다.

## 상태
- 반영됨
- 다음에서 일부 대체됨: [ADR: 플레이어 런타임 권한 ECS 이전 + 표현 브리지 경계 고정](ADR-20260303-02-player-ecs-authority-and-presentation-bridge-for-replay.md)

## 배경
- `OPS-001 #10`은 "재현 가능한 시드/리플레이 최소 기반"을 목표로 하지만, 현재는 문서상 `TODO` 상태다.
- 코드에는 일부 결정론 요소(`SpawnRunSeedComponent`, `SourceStableIdComponent`, clip 선택 RNG)가 존재하지만, 실제 탄 스폰 RNG와 입력 기록/재생 경로는 최소 기반이 없다.
- 회귀 버그의 재현 실패 원인을 줄이기 위해, 구현 전 재현 범위와 데이터 계약을 먼저 고정할 필요가 있다.

## 결정
1. 재현 범위를 최소 목표로 고정한다.
- 1차 목표: `동일 머신 + 동일 빌드`에서 동일 seed + 동일 입력이면 동일 결과를 재생 가능해야 한다.
- 크로스 플랫폼/버전 일치는 1차 범위에서 제외한다.

2. 리플레이 입력 단위를 `프레임 스냅샷`으로 고정한다.
- 입력 이벤트 변화분(delta) 대신 프레임 단위 스냅샷을 기록/재생한다.
- 이유: 프레임 경계 오차 및 이벤트 순서 차이에 의한 desync 리스크를 줄이기 위함.

3. RNG 키를 run seed 계열로 일원화한다.
- Request 단계(Poisson 등)와 Execution 단계(실제 스폰 위치/방향 샘플링) 모두 `GlobalRunSeed + SourceStableId + Sequence/Slot/Directive/Frame` 조합으로 키를 생성한다.
- `Entity.Index` 단독 의존은 재현성 리스크로 지양한다.

4. 적용 순서를 단계적으로 고정한다.
- 1단계: Request RNG(run seed 계열) 일원화
- 2단계: Execution RNG(run seed 계열) 일원화
- 3단계: 입력 Record/Playback 최소 루프 도입

## 대안 비교
### 대안 A: 현행 유지(부분 결정론만 유지)
- 장점: 변경 비용 최소
- 단점: 실스폰 RNG와 입력 경로 불확정으로 재현 실패가 계속 발생 가능

### 대안 B: 변화분 이벤트 리플레이
- 장점: 저장량이 작다
- 단점: 프레임 경계/순서 오차에 취약하고 디버깅 비용이 증가한다

### 대안 C: 전면 크로스플랫폼 결정론
- 장점: 재현 범위가 가장 넓다
- 단점: 현재 단계(OPS-001 #10 최소 기반) 대비 비용/복잡도가 과도하다

### 채택안 선택 이유
- 최소 구현 비용으로 회귀 추적 효율을 빠르게 끌어올리면서, 이후 범위 확장을 위한 데이터/키 계약을 먼저 고정할 수 있다.

## 결과
- 기대 효과:
  - "재현 안 됨" 이슈를 줄이고 버그 추적 시간을 단축한다.
  - 테스트에서 seed+입력 고정 케이스를 표준화할 수 있다.
- 리스크:
  - 스냅샷 기록량 증가
  - 기존 RNG 경로 변경에 따른 회귀 가능성
- 완화:
  - 단계적 적용(요청 -> 실행 -> 입력)
  - 기존 스모크/스트레스 테스트 + seed 고정 회귀 테스트 추가

## 후속
1. `Replay` 최소 컴포넌트/버퍼 계약 정의(모드, 프레임, 입력 스냅샷, 재생 커서)
2. Request RNG 키에서 `Entity.Index` 의존 제거
3. Execution RNG 키에서 `Entity.Index` 의존 제거
4. `same seed + same snapshot input => same outcome` 검증 테스트 추가
